## What this delivers — and the deployment boundary

The runbook (§5) and IP-0005 flagged that a fully-autonomous run must flow evidence **from the agent
via the court MCP**, not have it pre-declared in the backlog. B2.P builds that **seam**: the loop
sources evidence from a `CourtEvidencePool` the Builder submits to, so the agent produces its own
probative evidence (which B2.N/B2.O then verify and gate). The backlog path is unchanged when
`evidence_source` is `None`.

The **live** connection — the real `claude` Builder session submitting to a running `CourtServer` over
`claude --mcp-config`, whose submissions land in the pool keyed by the capability token's `run_id` —
is the **deployment step**, exactly parallel to the live `claude` call itself (built behind a seam,
wired at deploy). The `CourtServer` contract (`mcp:court:write`, B1.A) already exists; the pool is the
sink the deployment binds it to.

### 2–7. Drift / Duplication / Simplicity / Derivation / Debt

### 8. Security Implications
**PASS.** Autonomous evidence still passes the full gauntlet: live evidence binding (B2.I), probative
court (B2.N), vacuous-evidence gate (B2.O), and the adversary PASS gate (B2.K). The agent producing
its own evidence does not weaken any check — it strengthens honesty (no human-authored evidence).

### 9–10. Runtime / Extensibility
**PASS.** The pool is the seam a live `CourtServer` binds to; a durable/ledgered evidence pool can
replace the in-memory one without touching the loop.
