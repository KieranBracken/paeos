# 1. Research Thesis

PAEOS has demonstrated a dangerous implementation pattern:

```text
implementation written
        ->
tests written to fit implementation
        ->
same tests used to certify implementation
```

This permits rationalization.

A Builder can unconsciously encode its implementation assumptions into its tests and then receive apparent empirical confirmation from those tests.

The desired property is stronger:

> Acceptance behavior must be specified independently before implementation is permitted to satisfy it.

However, current constitutional findings indicate that adding a new lifecycle state such as:

`StageId.TEST_DESIGN`

may itself violate the canonical requirement that relevant CER rules:

> govern every state; add no state.

Therefore this research must NOT assume a new stage is required.

The primary candidate architecture is:

- strengthen L11's implementation contract with failing-test-first obligations;
- require L13 Verification Court to independently prove the baseline-fail → implementation-pass delta;
- route any constitutional change through the appropriate L19 amendment mechanism.

This remains a research hypothesis until confirmed against the canonical corpus.

---

# 2. Primary Research Question

## RQ-1

How should PAEOS structurally enforce test-first engineering so that tests genuinely constrain implementation rather than rationalize it, while preserving the canonical 19-layer lifecycle?

---

# 3. Failure Pattern

The system must prevent:

```text
Builder chooses implementation
        |
        v
Builder designs tests around implementation
        |
        v
tests pass
        |
        v
Court certifies self-authored assumptions
```

This is particularly dangerous when:

- implementation and tests are generated by the same model/context;
- acceptance criteria are vague;
- tests inspect implementation internals rather than required behavior;
- tests are created after architecture choices are already fixed;
- mutation checks prove only that code and tests co-depend, not that requirements were independently specified.

# 6. Test Artifact Immutability

Once implementation begins, the acceptance test bundle should not be silently rewritten.

Research mechanisms including:

- CAS hash of pre-implementation tests;
- L11-sealed test manifest;
- capability boundary preventing Builder modification;
- separate test-authoring role/context;
- explicit amendment/remand if tests prove incorrect.

Required property:

```text
test_hash_before_implementation
        ==
test_hash_used_by_court
```

unless a governed test-contract revision occurred.

---

# 7. Baseline Failure Semantics

"Test fails before implementation" alone is insufficient.

Bad example:

```text
test file is missing
-> pytest exits 4
```

That proves nothing about required functionality.

Court must establish that the same test exists in both environments and fails because the required behavior is absent.

Research how to classify baseline failure:

- assertion failure;
- expected contract violation;
- missing required API;
- deliberately unsupported behavior;
- infrastructure/tool failure;
- unrelated failure.

Only semantically probative failures should count.

# 8. Same-Test Controlled Experiment

The preferred verification model is:

```text
KNOWN PRE-CHANGE BASE
        |
        +--------------------+
        |                    |
        v                    v
CONTROL                  TREATMENT
new tests               same new tests
baseline code           candidate code
        |                    |
        v                    v
FAIL                    PASS
        +---------+----------+
                  |
                  v
             probative delta
```

Research whether workspaces should be constructed from an immutable git/CAS base rather than by reverting the current working tree.

---

# 9. Test Independence

Test-first timing does not fully solve correlated reasoning if the same model creates:

- requirements;
- tests;
- implementation.

Research increasing independence through:

- separate role/session;
- context isolation;
- heterogeneous model;
- contract-derived deterministic test generation;
- adversarial test review;
- requirement-to-test traceability.

Important:

> Different model brands are optional; independent information and authority boundaries are the primary goal.

---

# 10. Requirement-to-Test Traceability

Each acceptance criterion should map to explicit tests.

Candidate structure:

```yaml
requirement_id: REQ-004
source: L11_IMPLEMENTATION_CONTRACT
tests:
  - tests/foo.py::test_required_behavior
baseline_expected: FAIL
candidate_expected: PASS
```

Court should reject:

- acceptance criteria with no tests;
- tests with no requirement;
- tests that cannot discriminate the change;
- implementation behavior outside the stated contract where it creates architecture risk.

---

# 11. Test Modification During Implementation

Sometimes the pre-implementation test is genuinely wrong.

The system must permit correction without encouraging rationalization.

Research a governed mechanism:

```text
test contract found invalid
        |
        v
REMAND
        |
        v
test revision justified
        |
        v
new test hash established
        |
        v
baseline rerun
        |
        v
implementation resumes
```

Implementation should not simply edit failing tests until green.

        |

# 13. Interaction With Unit Tests

Not every test must necessarily be predetermined.

Research distinction between:

### Acceptance / contract tests
Must exist pre-implementation.

### Implementation-local unit tests
May be authored during implementation to improve internal quality.

### Regression tests
May be added when previously unknown defects are discovered.

### Property/invariant tests
May be constitutional or generated from stable invariants.

Structural test-first enforcement should focus primarily on tests proving the objective's externally required behavior.

---

# 14. Interaction With Ceremony Depth

Research whether Trace-A work may use a lighter test-first contract.

Even the lowest ceremony should not permit:

```text
implementation first
tests later
certify self
```

Possible Trace-A form:

- one minimal acceptance test bundle;
- deterministic baseline fail;
- implementation;
- Court fail→pass reproduction.

Higher ceremony may require:

- adversarial test design;
- property tests;
- mutation testing;
- multiple test categories;
- independent test reviewer.

Ceremony may scale test depth without eliminating the structural ordering.

# 17. Required Adversarial Scenarios

## A — Post-Hoc Test Rationalization
Builder creates implementation then writes tests.

Expected:
- Court rejects absence of pre-implementation test provenance.

## B — Test File Missing on Baseline
Baseline fails only because test file is absent.

Expected:
- evidence rejected as non-probative.

## C — Test Changed After Implementation
Builder weakens assertion after implementation.

Expected:
- hash mismatch / contract violation / remand.

## D — Wrong Test
Pre-implementation test is incorrect.

Expected:
- governed remand and contract revision;
- not silent Builder modification.

## E — Same Model Correlated Error
Test and implementation encode the same faulty assumption.

Expected research outcome:
- determine which independent review mechanism catches this.

## F — Implementation Passes Without Required Behavior
Test insufficiently covers acceptance criterion.

Expected:
- requirement-to-test completeness check detects gap.

## G — Trace-A Task
Cheap reversible change.

Expected:
- lightweight but genuine test-first proof, not exemption.

# 19. Acceptance Criteria

- [ ] Canonical placement is established from source documents.
- [ ] No unsupported new StageId is introduced.
- [ ] Acceptance tests are established before implementation authority begins.
- [ ] Pre-implementation test bundle has immutable provenance.
- [ ] Same acceptance tests execute against baseline and candidate.
- [ ] Baseline failure must be semantically probative.
- [ ] Candidate must pass the unchanged acceptance tests.
- [ ] Court verifies the fail→pass delta independently.
- [ ] Builder cannot silently weaken acceptance tests.
- [ ] Invalid tests can be corrected through governed remand.
- [ ] Acceptance criteria map to explicit tests.
- [ ] CANARY-0002 remains independently enforced.
- [ ] Ceremony-depth interaction is defined.
- [ ] Trace-A does not eliminate test-first ordering where testing is required.
- [ ] Required constitutional amendment path is identified.
- [ ] Negative tests prove post-hoc rationalization fails closed.

# 20. Anti-Goals

Do NOT:
- add `StageId.TEST_DESIGN` merely because it seems clean;
- turn every internal unit test into a constitutional artifact;
- require heavyweight TDD ceremony for trivial changes where a minimal contract suffices;
- allow Builder to modify acceptance tests silently;
- treat any baseline non-zero exit code as proof;
- confuse mutation testing with independent test design.
