## Design

- **Read-only by construction.** `Constitution` loads a corpus once into private maps and
  exposes only query methods. `Clause` and `ClauseLineage` are frozen. FR-1 is a property of
  the *type's shape*, not a checked precondition — the strongest form of the guarantee.
- **Content-addressed lineage.** `clause_hash(text)` matches `kernel.cas.content_hash`
  semantics, so `lineage(hash)` ties a constitutional clause into the same hash universe as
  the ledger and CAS — a hash reference anywhere can be resolved back to its clause.
- **Provisional clause syntax.** `[cN]` markers, id `"<document>#c<n>"` — mirrors SC-05 and
  the ClauseRef `"<parent>#c<n>"` shape. Provisional until DEBT-0004 ratifies the real corpus.

## Ordering invariant (founder confirmation, 2026-07-27)

At ratification the founder asked whether `query()` guarantees deterministic ordering
**across all conformant implementations**. Finding and resolution:

- **In fact, deterministic.** `query`/`clause_ids` sort by `(document, ordinal)` with
  `ordinal` as an integer. Because duplicate clause ids are rejected at construction
  (`DuplicateClause`), `(document, ordinal)` is a *unique* key, so the sort is a total order
  fully determined by the *set* of matching clauses — independent of load order, dict
  iteration, or backend. No tie-break can vary.
- **But not yet *binding*.** As written it was an artifact of the `sorted()` call, not a
  documented clause of the interface contract; a different conformant backend could have
  returned another order. So strictly "across all conformant implementations" was **not**
  guaranteed.
- **Resolution.** Elevated to a **binding, documented, tested invariant** (no algorithm
  change): the canonical order `(document, ordinal)` ascending (numeric ordinal, so `c2`
  precedes `c10`), `documents` ascending. Stated in the `Constitution` class contract and
  the `query` docstring; pinned by two conformance tests — `test_query_ordering_is_canonical_numeric`
  (numeric not lexical) and `test_query_ordering_is_insertion_independent` (same corpus built
  in three different insertion orders ⇒ byte-identical sequences). Two conformant accessors
  over byte-identical corpora now return byte-identical results — a precondition for
  deterministic replay (B0.10) and for any evidence that cites `query` output.

## Adversary pass (T4)

1. **Mutate a returned clause** → `FrozenInstanceError` (tested). ✓
2. **Mutate a query result list** → corpus unaffected; results are copies (tested). ✓
3. **Forge a `Clause` and try to install it** → no setter, no write API; `get_clause` still
   returns the loaded instance (tested). ✓
4. **Reach the filesystem through the accessor** → the module opens no write handle
   (`open(` absent; only `read_text`), so there is no code path to disk mutation (grep test). ✓
5. **Boundary honesty** — the accessor guarantees *the runtime cannot alter Z0 through it*.
   It does **not** guarantee the on-disk `constitution/` files are themselves unaltered by a
   process outside PAEOS; that is the CI TCB gate F2 (kernel/constitution touch → HARD-LOOP)
   plus the append-only git history's job, not the accessor's.
