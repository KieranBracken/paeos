## Design (K9 narrow waist, mirrors B0.1)

Addressing / verification / GC logic lives in the TCB (`CAS`) over a tiny `CasStore`
Protocol (`write`/`read`/`exists`/`delete`/`iter_keys`). Two backends:

- **`InMemoryCasStore`** — fast reference backend.
- **`FilesystemCasStore`** — durable: blobs are files named by hash, git-style two-char
  sharding (`<root>/<key[:2]>/<key[2:]>`), **atomic writes** (temp file + `os.fsync` +
  `os.replace`) so a crash never exposes a partial blob.

**The address is the checksum.** `get` re-hashes the retrieved bytes and raises
`CasCorruption` on mismatch — bit-rot/tamper detection for free, the CAS analogue of the
ledger's `verify_chain`. Crucially, **B0.2 needs no database**: content-addressed files are
durable on their own, so the restart test passes for real and this task does **not** depend
on DEBT-0003 (that debt is the *ledger's* durable backend).

## The six questions (CER-4)

**(a) Architectural weaknesses discovered?**
One, caught in the Adversary pass *before* the review and fixed: a crash mid-write leaves a
`.tmp` file inside the shard directory, which the first cut of `iter_keys` would have
yielded as a bogus key (polluting counts and GC). Fixed: `iter_keys` yields only
well-formed addresses (`is_valid_hash`), so orphaned temp files are invisible. Regression
test `test_orphaned_temp_file_is_not_a_key`.

**(b) Assumptions invalidated?**
None. Notably the assumption that "durable persistence ⇒ needs the DEBT-0003 backend" is
*false for the CAS*: content-addressing makes the filesystem a sufficient durable store.
This narrows DEBT-0003 to the ledger, where ordered single-writer ACID append genuinely
needs a database.

**(c) Which parts of PAEOS became stronger?**
The source of truth is now complete for Phase 0's foundation: the ledger orders events, the
CAS stores the bytes they reference. Content-addressing gives every artifact a stable,
verifiable identity — the precondition for the seal (B0.9), projections (B0.10), and any
`ArtifactRef` in the kernel schema.

**(d) Improvement Proposals created?**
None.

**(e) Architectural Debt recorded?**
None new. GC reachability is supplied by the caller (a mark set); wiring the *source* of
reachability (from ledger/artifact refs) is a later integration concern, not a debt — the
CAS correctly owns only "don't collect what I'm told is reachable."

**(f) Should implementation strategy change?**
No. The narrow-waist-first pattern held for a second module and paid off again (the backend
swap and the orphan-file fix were both contained to the store layer).

## Adversary pass

1. **Tamper under a valid address** — mutate stored bytes (memory *and* on disk) → `get`
   re-hashes and raises `CasCorruption` (both tested). ✓
2. **Malformed address** — `get("not-a-hash")` → `ValueError`; `has` → simply `False`,
   no crash. ✓
3. **Crash mid-write** — atomic `os.replace` means no partial blob is ever visible under
   its final name; orphaned `.tmp` is excluded from `iter_keys` (fixed + tested). ✓
4. **GC over-collection** — `gc` never deletes a hash in the reachable set; empty reachable
   collects all; dangling reachable refs are ignored, not "repaired" (all tested). ✓
5. **Boundary honesty** — like the ledger, this defends integrity, not authenticity: a
   writer with total store access can delete-then-repopulate. The outer layers (append-only
   grants, the seal, GC gated by real reachability from the ledger) own that; B0.2 owns the
   innermost content-integrity layer.
