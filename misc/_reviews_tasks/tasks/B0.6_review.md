## The failure→outcome routing (derivation — please ratify)

7.6 §4 step 6 says "on fail: REMAND | REJECT | QUARANTINE," and 7 §4.4 gives the *triggers* for
each, but does not enumerate which four-tuple failure maps to which outcome. Derived mapping,
from §4.4's trigger list + the 7.5 security posture:

| Failed check | Outcome | Rationale (§4.4 trigger) |
|---|---|---|
| Forged/tampered token, role-relabel, op-escalation | **QUARANTINE** | "capability-escalation attempt" — FR-2/FR-3 tripwire |
| Expired token | **REJECT** | stale/invalid request; not a system-freeze (deny this transition) |
| Illegal edge (`is_legal` False) | **REJECT** | malformed request; unsealable-shaped |
| `produced_against` ≠ artifact under review | **REMAND** | SI-4 rebind — fixable |
| Claim with no evidence | **REMAND** | deny-by-default; produce evidence — fixable |
| Stale evidence binding | **REMAND** | SI-4 — rebind to the correct artifact |
| Evidence forgery (reproduction mismatch) | **QUARANTINE** | T2 forgery = integrity breach |
| Evidence not reproducible (bad/absent command) | **REMAND** | fixable — re-produce |
| Separation-of-powers violation | **QUARANTINE** | SI-3 breach = escalation-class |
| HARD change (TCB, via classifier) | **REJECT** | refuse here; route to G-Amend |
| all pass | **COMMITTED** | — |

**Judgment calls flagged for ratification (Observation 1):** expired-token → REJECT (not
QUARANTINE); stale-evidence → REMAND (not QUARANTINE). Both treat *staleness* as recoverable and
reserve QUARANTINE for *attacks*. `ABORT` is intentionally not produced here — it is the
intake/triage disposition (§4.4), not a four-tuple failure.

## Evaluation Checklist

### 1. Constitutional Compliance
**PASS.** Deny-by-default (FR-4); the four checks are exactly 7.6 §4 steps 1–4; failure routing
uses only §4.4 outcomes. No new authority or invariant.

### 2. Architectural Drift
**PASS.** Pure composition — no re-implementation of capability/evidence/lifecycle logic; it
*calls* B0.5/B0.7/B0.8. `SEPARATED_POWERS = {BUILDER, VERIFIER, ADVERSARY, RATIFIER}` maps §5.1's
Build/Verify/Adversary/Seal (Seal⇒RATIFIER; Critic/Planner/Doc excluded per §5.1) — Observation 2.

### 3. Duplication of Mechanisms
**PASS.** Zero duplication; the gate is the single composition point.

### 4. Bypassing Mechanisms
**PASS.** Checks run in the §4 order (authority → goal → evidence → validation); a forged token
never reaches the evidence path. Evidence is resolved through an injected resolver, so the gate
cannot be handed pre-trusted objects out of band.

### 5. Simpler Implementation Possible
**PASS / minimal.** One method, one `_deny` helper. Dependencies are injected (broker, resolver,
optional classifier) rather than imported-and-constructed, keeping it testable and unentangled.

### 6. Better Derivation
**PASS.** The five steps map 1:1 to the §4 pseudocode; the routing table is the derivation of §4.4.

### 7. Hidden Technical Debt
**PASS.** Two seams are explicit, not hidden: `committed_seq` is assigned by the ledger append
(B0.1) at the control plane (B0.12) — the gate returns the *decision*; step-5 classification is a
pluggable hook wired by B0.11. Neither is debt (both are ratified-DAG boundaries).

### 8. Security Implications
**PASS — this is the enforcement point.** Adversary pass below. Every non-COMMITTED path is a
typed denial; attacks route to QUARANTINE (human), recoverable gaps to REMAND. The gate holds no
key and appends nothing itself.

### 9. Runtime Implications
**PASS.** One subprocess per deterministic evidence (bounded by B0.7's timeout); otherwise pure.
Exceptions from dependencies are all caught and mapped — no leak.

### 10. Future Extensibility
**PASS.** B0.11 classifier and B0.1 ledger wire in through the existing hook/return; B0.9 seal is
a separate gate. The injected-dependency shape composes into B0.12's control plane unchanged.
