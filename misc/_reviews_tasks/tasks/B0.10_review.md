## Evaluation Checklist

### 1. Constitutional Compliance
**PASS.** The ledger is the source of truth; a projection is an explicitly-verifiable *cache*.
`verify_against_head` re-derives from the ledger and rejects stale/poisoned projections *before
use* (§6, D1). Deterministic replay (byte-identical state + head across runs) is proven, incl. the
1k-event corpus (B0.10 acceptance).

### 2. Architectural Drift
**PASS.** No domain schema baked in — the engine is generic over `S` via a `Projector`. Uses PEP-695
type parameters (py3.12, §3 toolchain). Canonical digest is the caller's, matching the repo's
sort-keys/no-whitespace hashing discipline in the test projector.

### 3. Duplication of Mechanisms
**PASS.** Reuses `Ledger.read`/`head_hash` (B0.1) as the single fold source. Observation 1: the
B0.9 seal index is a hand-rolled projection that could later be expressed as a `Projector` — a
consolidation, not duplication introduced here.

### 4. Bypassing Mechanisms
**PASS.** `replay` reads the ledger in seq order only; it writes nothing. Verification does not
trust the projection's cached `state_digest` field — it recomputes from the *state* (see §8).

### 5. Simpler Implementation Possible
**PASS / minimal.** A protocol, a frozen record, and two functions. No caching layer, no
incremental machinery (Observation 2).

### 6. Better Derivation
**PASS.** replay = fold; verify = re-derive-and-compare. This is the most direct expression of
"the ledger is truth, the projection is a checkable cache."

### 7. Hidden Technical Debt
**PASS.** None. The two seams (seal-index consolidation, incremental replay) are observations for
later tasks, each additive.

### 8. Security Implications
**PASS — T7 closed.** A **stale** projection (ledger advanced) → `StaleProjection`. A **poisoned**
projection (state tampered) → `PoisonedProjection`. Crucially, verification recomputes the digest
from `projection.state` against a fresh replay, so an attacker who tampers the state *and* updates
the cached `state_digest` field to match is **still caught** (explicit test
`test_poison_hidden_behind_a_matching_digest_field_is_still_caught`). Deny-before-use.

### 9. Runtime Implications
**PASS.** `replay`/`verify` are O(ledger) folds, no I/O beyond the ledger read, no leaks. For a
large ledger, verification cost = one replay (Observation 2).

### 10. Future Extensibility
**PASS.** Any read-model (goal state, seal index, budget, projections for the CLI `inspect`, B0.12)
is a `Projector`. Incremental/checkpointed projections drop in behind the same `replay`/`verify`
contract when performance requires.

## Adversary pass (T7 — projection poisoning)

1. **Stale projection** (build, then append to the ledger) → `StaleProjection` (tested).
2. **Poisoned state** (tamper a goal's stage in the cached projection) → `PoisonedProjection`
   (tested).
3. **Poison + matching digest field** (also forge the cached `state_digest`) → still
   `PoisonedProjection`, because verify digests the *state*, not the field (tested).
4. **Determinism** — two independent replays of the 1k corpus are byte-identical (state digest +
   head) (tested), so re-derive-and-compare is a sound integrity check.

## OBSERVATIONS
1. **Seal-index consolidation.** B0.9's in-memory idempotency index (rebuilt ad hoc from the
   ledger) is a special case of a `Projector`; a later task could express it as one for uniformity.
   Not required now — B0.9 works and is tagged.
2. **Verification is a full replay.** Correct but O(ledger); incremental replay + periodic
   checkpoints are an additive optimization for large ledgers, not needed for Phase 0.
