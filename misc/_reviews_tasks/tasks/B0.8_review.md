## Evaluation Checklist

### 1. Constitutional Compliance
**PASS.** Enforces the T1/A-6 invariants: unforgeable (Ed25519 over `bound_to`+`operations`+TTL),
bound & immutable in use (SI-3, no relabeling), TTL'd (A-6), least-authority allow-list
(deny-by-default, FR-4). Signing key held in the broker, never exposed (A-5). Uses the ratified
`CapabilityToken`/`CapabilityBinding` types (B0.4) — no re-declaration.

### 2. Architectural Drift
**PASS.** No new concept. The canonical signing payload is deterministic JSON (sort_keys, no
whitespace, ASCII) — the same discipline as the ledger/CAS/constitution hashing, not a new
scheme. Enum values (`stage.value`, `role.value`) are signed, so the wire form is stable.

### 3. Duplication of Mechanisms
**PASS.** Reuses `CapabilityToken`, `CapabilityBinding`, `StageId`, `Role`, `Ts` from
`kernel/types.py`. Ed25519 via pynacl (the §3-pinned primitive), not a hand-rolled MAC.

### 4. Bypassing Mechanisms
**PASS.** `verify` checks in the order **signature → TTL → binding → allow-list**, so a forged
token fails on signature before any field is trusted (tested: `test_verify_order_signature_before_binding`).

### 5. Simpler Implementation Possible
**PASS / minimal.** One broker class, two methods, a canonical-payload helper. A symmetric MAC
(HMAC) would be simpler and sufficient (kernel mints *and* verifies), but §3 pins Ed25519 and
the field is a `Sig`(nature); using the pinned primitive avoids a silent crypto substitution.

### 6. Better Derivation
**PASS.** `mint`/`verify` map 1:1 onto §7's contract and the T1/A-6 hardenings; nothing composed
that the spec separated.

### 7. Hidden Technical Debt
**PASS.** None. Key persistence is an explicit interface seam (Observation 1), not hidden debt.

### 8. Security Implications
**PASS — this is the reference monitor.** Adversary pass below. Every failure path is a *denial*
with a specific exception; the safe direction (deny) is the default. The signing key never leaves
the broker; `verify_key_hex` exposes only the public key. F3 confirms no key material is committed.

### 9. Runtime Implications
**PASS.** `mint`/`verify` are pure w.r.t. external state (one in-memory key); Ed25519 sign/verify
are microsecond-scale; no I/O, no blocking, exceptions typed.

### 10. Future Extensibility
**PASS.** B0.6 gates call `verify` as `propose_transition` step 1. If operation *scoping* is later
required (prefix match on `cas:write:<scope>`), it extends the allow-list check without touching
mint/signature (Observation 2).

## Adversary pass (T1 escalation + A-6 stale reuse)

1. **Fabricate a token** (hand-built `CapabilityToken`, no key) → `InvalidToken` (tested). No self-grant.
2. **Relabel role** (`replace` bound_to.role BUILDER→VERIFIER) → `InvalidToken`: signature covers
   bound_to (tested). And a *genuine* BUILDER token used as VERIFIER → `BindingMismatch` (SI-3, tested).
3. **Escalate operations** (`replace` to add `seal`) → `InvalidToken` (tested); using a granted token
   for a non-listed op → `OperationNotPermitted` (tested).
4. **Extend TTL** (`replace` expires_seq) → `InvalidToken` (tested).
5. **Stale-token reuse** (current_seq past expiry / before issue) → `ExpiredToken` (A-6, tested;
   boundaries inclusive).
6. **Cross-key** (token from another broker) → `InvalidToken` (tested).
7. **Boundary honesty:** the broker generates an *ephemeral* key by default; a *persistent* kernel
   key (ops/keys/, founder-owned rotation, A-5) is required for cross-process verification and for
   B0.9's seal — surfaced as Observation 1, not silently assumed.

## OBSERVATIONS

1. **Key persistence is an ops seam.** `CapabilityBroker(signing_key=...)` accepts a key but
   defaults to ephemeral generation. Real deployment loads a persistent Ed25519 key from `ops/keys/`
   (gitignored, F3-enforced, founder-owned rotation, A-5). B0.9 (seal) needs the same persistent key;
   recommend establishing the kernel keystore there. Not debt — the interface already admits it.
2. **Operation matching is exact.** `operation in token.operations` is an exact-string check
   (deny-by-default). If scoped ops like `cas:write:<scope>` later need prefix/glob semantics, that
   is an additive allow-list refinement; exact match is the conservative choice for now.
