## Evaluation Checklist

### 1. Constitutional Compliance
**PASS.** The dispatcher productionizes the DEBT-0002 spike as 7.6 §5 prescribes: mint a scoped
capability (the agent's only authority), compile context, build a `TaskPackage`, spawn a scoped
session, and **enforce `write_scopes`** on the result (agent has no ambient authority). The durable
ledger keeps the hash-chain algebra unchanged (FR-5); the SQLite backend only stores/returns rows.

### 2. Architectural Drift
**PASS.** `TaskPackage`/`TaskResult`/… are verbatim 7.6 §5. The SQLite store implements the *existing*
`LedgerStore` Protocol — no ledger-algebra change. The spawn is behind an `AgentRuntime` Protocol, so
no agent-runtime SDK is baked in (Observation 1). The context compiler is the deterministic core of
PAEOS-9A behind a `compile()` seam.

### 3. Duplication of Mechanisms
**PASS.** `within_scopes` reuses the classifier's normalise-then-prefix discipline (traversal-safe);
the ledger algebra, broker, CAS, and compiler are reused, not re-implemented.

### 4. Bypassing Mechanisms
**PASS.** A scope-violating write is refused **before** it can become an artifact (nothing lands in
CAS); a partial escape fails the whole dispatch (no partial artifacts). The capability grants exactly
the requested MCP servers, nothing more.

### 5. Simpler Implementation Possible
**PASS.** SQLite (stdlib) is the smallest durable single-writer backend; the dispatcher is one method
over injected dependencies.

### 6. Better Derivation
**PASS.** Context determinism (same inputs ⇒ same `content_hash`, order-independent) is the exact
PAEOS-9A property (K2); the durable store leans on SQLite's native single-writer for FR-5.

### 7. Hidden Technical Debt
**PASS.** DEBT-0003 is *repaid* (durable capability provided) and re-scoped to a LOW-priority Postgres
scale-swap (Observation 2). No new hidden debt.

### 8. Security Implications
**PASS — this is the agent boundary.** Adversary T9 below. `write_scopes` are enforced by the
dispatcher (traversal cannot escape), on top of the scoped-workspace spawn (DEBT-0002). The trace is
persisted immutably in CAS (audit). The agent never holds the kernel key; its token grants only its
MCP allow-list.

### 9. Runtime Implications
**PASS.** SQLite WAL + `synchronous=FULL` for durability; dispatcher is synchronous around the spawn
seam. Errors are typed (`ScopeViolation`, `ForkRejected`, `SingleWriterViolation`).

### 10. Future Extensibility
**PASS.** The real Claude Agent SDK adapter implements `AgentRuntime` (Observation 1); B1.C/D/E/G
dispatch through the same method; Postgres swaps behind `LedgerStore`.

## Adversary pass (T9 — scope escape)

1. **Write outside scope** (`constitution/…` under a `kernel/` scope) → `ScopeViolation`; **nothing
   lands in CAS** (tested).
2. **Traversal** (`kernel/../constitution/x`) → normalised, out of scope → `ScopeViolation` (tested).
3. **Partial escape** (one in-scope + one out-of-scope write) → whole dispatch refused (tested).
4. **Capability minimality** — token operations == exactly the requested MCP servers (tested).

## OBSERVATIONS
1. **`AgentRuntime` is a mock in tests; the real adapter is the integration step.** The spawn seam is
   validated by the DEBT-0002 spike; wiring the production adapter (Claude Agent SDK / `claude` CLI +
   real worktree isolation + MCP allow-list from `permissions`) is the remaining B1.B integration and
   may need an SDK dependency + the target env. The dispatcher *logic* (the security-critical part) is
   complete and tested against the contract.
2. **DEBT-0003 → SQLite now, Postgres at scale.** Founder decision recommended: accept SQLite as the
   Phase 1–2 durable backend (no docker; FR-5 by nature), with Postgres as a Phase-2/3 scale swap
   behind the same Protocol.
3. **Context compiler is the PAEOS-9A core, not the whole.** Deterministic assembly + freshness hash
   (K2) are here; canonical loading order / truncation budgets / overlay elaborate behind `compile()`.
