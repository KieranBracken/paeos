## What this delivers

PAEOS-7 §8 Phase-2 component 1 and "the reason PAEOS exists" (§7): a run that fails makes the next
run less likely to fail. `EvolutionLayer.run(outcome, goal_signature, changed_paths)` runs the four
evolution stages over a completed run:

- **RETROSPECT (15)** — extract findings from the `RunOutcome`; classify the implicated paths with
  the *kernel* classifier, not a claim (A-2).
- **EVOLVE (16)** — draft a soft **scar** (lesson + detection signature, FR-6) for every failure;
  and, for a **TCB-implicated recurrence** (a guarded failure that repeated), a hard
  **IMPROVE_RUNTIME proposal** (§7.4 / A-3).
- **MEMORY_UPDATE (17)** — write the scar drafts into the shared `ScarStore` (a gated transition —
  an over-broad signature is *quarantined*, not written; T3).
- **IMPROVE_RUNTIME (18)** — emit `AmendmentProposal`s. The layer **only proposes**; it never routes
  to the amendment path and never applies anything (CER-5). A test drives an emitted proposal into
  B2.E's gate, which halts at `AWAITING_RATIFICATION` — the closed self-improvement loop.

## Evaluation Checklist

### 1. Constitutional Compliance
**PASS.** The layer proposes; it never legislates (CER-5). Amendment proposals flow to the B2.E
human gate; nothing is auto-applied. A clean SEALED run yields no scar and no proposal — learning is
from failure (§7.1). The kernel classifies blast radius (A-2), so a proposal only arises for a
genuinely TCB-implicated recurrence.

### 2. Architectural Drift
**PASS.** Reuses the `ScarStore` (B1.F), the kernel classifier (B0.11), and the `AmendmentProposal`
type (B2.E) unchanged. No new mechanism, no new authority. `Retrospective`/`EvolutionResult` are
plain records.

### 3–7. Duplication / Bypass / Simplicity / Derivation / Debt
**PASS with a surfaced ambiguity.** Wiring the layer into the live self-host loop collides with the
**ratified** B1.F inline remand-scar: the coarse inline scar is a subset of every remand's evolution
signature, so recurrence would falsely fire on first failure. Per the founder's directive and CER-6,
this is treated as a **constitutional ambiguity, not an implementation problem**: the conflict is
documented in **PAEOS-IP-0004** (existing behaviour, the conflict, four architectural options,
recommended resolution = Option A, constitutional derivation, implementation impact) and **left
unimplemented**. B2.F ships on **ratified behaviour only** — the Evolution Layer is delivered
standalone and is **not** wired into `SoftLoop`/`SelfHostRunner`. No ratified behaviour was modified.

### 8. Security Implications
**PASS.** T3 (memory poison) is guarded: MEMORY_UPDATE goes through `propose_scar`, so an over-broad
signature is quarantined, not written; the layer surfaces the quarantine rather than forcing it. The
layer holds no authority and applies nothing.

### 9–10. Runtime / Extensibility
**PASS.** `EvolutionLayer` takes an injected shared `ScarStore`, so it composes over any run source.
The recurrence→proposal trigger is a single, derivable rule; broadening EVOLVE to skills/checklists
(soft self-improvement) drops in behind the same `run` entry point.

## Adversary / property pass

1. **Clean seal → no guard** — a SEALED outcome yields no scar, no proposal (tested).
2. **Failure → scar** — a REMANDED outcome writes a goal-tagged scar, matchable for a later goal
   (FR-6, tested).
3. **First vs recurrence** — a first TCB failure emits only a scar; a *recurrence* emits an
   IMPROVE_RUNTIME proposal; a SOFT recurrence emits none (tested).
4. **Closed loop, human-gated** — an emitted proposal enters B2.E and halts at
   `AWAITING_RATIFICATION`, `applied` False (tested).
