## Design (K9 narrow waist)

The hash-chain algebra lives in the TCB and is storage-agnostic behind `LedgerStore`
(a `Protocol`: `acquire_writer`/`release_writer`/`head`/`append_row`/`read`/`count` — **no
update or delete exists**, so append-only is enforced by the *shape of the interface*, not
by discipline). `InMemoryLedgerStore` is the reference backend the property tests drive.

- **Append-only**: the only mutating method is `append`; rows are frozen dataclasses.
- **Hash-chained**: `row_hash = sha256(canonical(prev_hash, seq, timestamp, event))`,
  canonical = sorted-key, NaN/Inf-rejecting, ASCII JSON → deterministic and recomputable
  from stored fields alone (so replay, B0.10, is byte-identical).
- **Single-writer (FR-5)**: constructing a `Ledger` claims the store's writer token; a
  second distinct writer is refused until the first releases.

## The six questions (CER-4)

**(a) Architectural weaknesses discovered?**
One, surfaced honestly below in §Adversary: `verify_chain()` proves *tamper-evidence for
point mutations*, not *authenticity of the whole history*. This is by design (integrity ≠
authenticity) but must be named so no later task over-trusts it.

**(b) Assumptions invalidated?**
None constitutional. One implementation choice forced by environment: **no docker daemon
is available here**, so a Postgres backend cannot be run or iterated locally — only blind
in a CI service. Building the TCB's foundation blind against an un-runnable backend would
be reckless, so the Postgres backend is deferred behind the `LedgerStore` waist (see
Recommendation). The §3 Postgres lock is **not** revoked — the production backend still
implements this exact Protocol; only its *timing* moves.

**(c) Which parts of PAEOS became stronger?**
FR-5 moved from prose to an executable, property-tested invariant. The source of truth now
exists: every future module (CAS, projections, seal, CLI) derives from this. The single-
writer + fork guards give the chain a *total order*, which is the precondition for
deterministic replay (B0.10) and for the seal binding a unique head (B0.9).

**(d) Improvement Proposals created?**
None. B0.1 revealed no constitutional improvement.

**(e) Architectural Debt recorded?**
**DEBT-0003** — a **durable production persistence backend** (durable, append-only, single-
writer storage behind `LedgerStore`) is not yet implemented; B0.1 runs on the in-memory
reference backend. The roadmap's current target for this capability is PostgreSQL 16, but
the debt records the missing *capability*, not a permanent engine choice. Repayment: **by
B0.10** (whose cross-restart replay acceptance forces a durable backend). Non-blocking for
B0.2–B0.9, which are storage-agnostic against the Protocol.

**(f) Should implementation strategy change?**
No. The narrow-waist-first approach (prove the algebra in-memory, drop the durable backend
in behind the Protocol) is the right pattern and should recur for every substrate the
playbook isolates (e.g. Temporal behind `durable_substrate.py`).

## Adversary pass (T7 + beyond)

I attacked my own ledger, not just the fork:

1. **T7 fork** — forge a second row at an existing seq → `ForkRejected` (tested). ✓
2. **Point tamper** — mutate any single field of any row → `ChainCorruption` (tested,
   property). ✓
3. **Row drop / reorder** — excise a row → seq-gap / broken-link caught (tested). ✓
4. **Full-history rewrite** — a writer with *total, direct* store access rewrites **every**
   row with internally-consistent recomputed hashes. This **passes** `verify_chain()`.
   This is the honest boundary: `verify_chain` is not a defense against an omnipotent
   writer, it is tamper-*evidence* for anything less. The layered defense is: append-only
   storage grant (Postgres: no UPDATE/DELETE to the runtime role), single-writer, the
   Ed25519 **seal over the head** (B0.9), and external anchoring (7.5 A-9, Phase 2). B0.1
   correctly owns only the innermost layer; the review records that the outer layers are
   *required* and not yet present.
